# 設計: 人が学べる教訓

[← ロードマップ](../../../ROADMAP.ja.md) · English: [learning.md](../learning.md)

状態: 提案（2026-10-08）。できているのは、作業順の 1 と 2（事件簿。関連する事件はまだ。[事件簿](../../ja/analysis.md#事件簿)を参照）と
4（ハブ）、そして 2026-10-09 の「仕事から学ぶ」です。すべての学びを分野別のライブラリーにまとめ、どれも最初から通して
読めます（事件簿の現場・問い・答え、説明、外れた手がかり、分析で見つかった原則・確認事項・図）。作業メモと復習の目印は
ブラウザーに残ります。先に問う形式は「すべてのナレッジ」に残っています。測定を含む残りをいつ予定しているかは
[ロードマップ](../../../ROADMAP.ja.md)にあります。

Chronicle はセッションごとに学んだことを書き留めますが、今はそのほとんどがエージェントに渡っています。MCP ツールと、
セッション開始時のメモです。人は同じ教訓を一覧で見るだけです。チームのハブと共有しているコンピューターでは、チームメイトの
教訓は **設定 › デバイス** に件数として出るだけで、エージェントのほうはすべてを受け取っています。エージェントが覚えているので、
人は覚えなくて済んでしまいます。

このページは、Chronicle が人の学び（エンジニアとして、アーキテクトとして）も助ける方法を説明します。

## 研究からわかること

学習科学、AI の支援とスキル形成、チームの学び方、ナレッジを生かし続けるプロダクトについて調べ、次の結論に至りました。

- **エージェントは、学びが起きる苦労を肩代わりしてしまう。** 主にジュニアの開発者 52 人の比較実験では、AI アシスタントを
  使って新しいライブラリを学んだ人のあとのテストの点は 50%、手で書いた人は 67% で、差はデバッグでいちばん大きく出ました
  （[Shen & Tamkin, 2026](https://arxiv.org/abs/2601.20245)）。作業を任せずに AI に質問した人は、学びをほとんど失いません
  でした。
- **教訓を読むことは、学ぶことではない。** 答えを思い出してからフィードバックを見るほうが、読み返すより g = 0.73 ほど効果が
  あります（[Rowland, 2014](https://doi.org/10.1037/a0037559)）。AI の要約で学んだ人は、同じ事実でも自分で調べた人より浅い
  知識にとどまりました（Melumad & Yun, PNAS Nexus, 2025）。教訓のカードはまさにその要約です。
- **新しい問題に生きるのは、事例と比較。ルール 1 つだけでは生きにくい。** 2 つの事例を比べると、1 つを学ぶより d = 0.50
  効果があります（[Alfieri et al., 2013](https://files.eric.ed.gov/fulltext/ED528947.pdf)）。失敗を情報として扱う訓練は、
  失敗を避ける訓練より効果があり、慣れない課題ではとくに差が出ます（Keith & Frese, 2008）。
- **チームは、失敗を安心して共有できるときに学ぶ。** 人ごとの件数は、人に共有をやめさせます。DORA と SPACE フレームワークの
  著者は個人単位の指標に警告しています。人は教訓の出どころとして名前を出し、数字にはしません。
- **少しずつ、定期的に、寛容に。** 人が戻ってくるプロダクトは、一度に求めることがとても少なく、溜まった未消化分を作りません。

注意点として、コーディングエージェントのセッションから学ぶことを試した研究はまだありません。学習科学の多くは学生や実験室の
課題によるもので、働く開発者に当てはめるのは推定です。そのため、この設計は効果を測る方法で締めくくります。

## すべての部分に共通するルール

1. **教える前に問う。** 大事な教訓は状況から始め、答えを見せる前に「あなたならどうするか」を尋ねます。
2. **いつでも飛ばせる。** キー 1 つで問いを飛ばせます。飛ばし続ける人には、もう尋ねません。
3. **エージェントには常にすべての教訓を渡す。** ここで説明するものは、どれもエージェントからナレッジを取り上げません。
4. **人は教え手として名前を出す。** 「Ana さんのセッションで学んだこと」とし、人ごとの件数は出しません。
5. **一人ひとりの学びのデータは、その人のコンピューターに残す。** ハブに届くのは、あったとしてもチーム全体の合計だけで、
   本人が選んだときだけです。
6. **決まった語彙と、実在の出典。** 原則、弱点の ID、スキルは決まった一覧から選び、参考文献は選び抜いたライブラリーから
   出します。モデルはそこから選ぶだけで、原則や出典を作り出しません。

## 1. 事件簿（ケースファイル）

gotcha、修正、決定を、事件簿の形で見せます。

| 部分 | 中身 | 出どころ |
|---|---|---|
| 現場 | 症状。何が見えたか、どんなエラーか | 分析で取り出す新しい項目が必要 |
| 外れた手がかり | 試してみて違っていたこと | 分析で取り出す新しい項目が必要 |
| あなたの見立て | 問いと、選べる 3 つの答え（飛ばしてもよい） | 本当の修正と、本当の行き止まり |
| 結論 | 原因と修正 | 教訓の本文 |
| ルール | 覚えておく 1 行 | 教訓のタイトル |
| 状態 | 解決（決定なら裁定）、1 回確認、または ×N で裏付け | 教訓の信頼度の段階 |
| 担当 | 誰がどのエージェントと取り組んだか | セッション。ハブでは、どの人のセッションが述べたか |
| 関連する事件 | 同じルールのほかの事件を並べて | 原則かルールが同じ教訓 |

決定はそれ自体が 1 つの事件として読めます。問い、検討した選択肢、裁定、その結果（何が楽になり、何が難しくなったか）です。
コマンド、事実、好みは、今までどおりの参照用カードのままです。

間違いの選択肢は、そのセッションで実際に行き止まりだったものでなければならず、答えを見せるときに間違いだと示します。
モデルが作った選択肢は、誤ったことを教えかねません。追加する項目は、ロードマップにある「理由付きの教訓」を広げるものです。
分析は各コンピューターで行うので、ナレッジだけを受け取るハブにも届きます。

## 2. アーキテクトの視点とトラック

各事件は、どの設計原則を示しているかも伝えます。修正だけでなく原則を学べるようにするためです。事件の下の「アーキテクトの
視点」には、原則、このバグを超えてどう当てはまるか、考えるための問い、1〜3 件の参考文献が入ります。

**アーキテクトのトラック** は、事件を原則ごとにまとめます。原則ごとに要約、その事件、カタ（その人のプロジェクトについての
設計の問いで、正解は 1 つではない）、参考文献の一覧があります。トラックの進み具合は本人にしか見えません。

Chronicle 自身のアーカイブにある事件から作った、最初の原則の一覧です。

| 原則 | Chronicle 自身のセッションでの例 | 参考文献 |
|---|---|---|
| 何が動いているかを知る | ダッシュボードが起動時に一度読んだ Web ファイルを配信し続けた | [The Twelve-Factor App: Build, release, run](https://12factor.net/build-release-run) |
| キャッシュを無効にする鍵 | 同じ 1 秒のうちに編集して戻したら、Python が古い `.pyc` を使い続けた | [PEP 552](https://peps.python.org/pep-0552/) |
| スキーマの進化 | 新しいテーブルが既存のデータベースに届かなかった。Bob がフィールド名を変えた | [Evolutionary Database Design](https://martinfowler.com/articles/evodb.html)、[Tolerant Reader](https://martinfowler.com/bliki/TolerantReader.html)、Kleppmann『データ指向アプリケーションデザイン』4 章 |
| 信頼の境界 | プロキシの後ろで、訪問者の `Host` ヘッダーがローカルに見えた | [OWASP: Host header injection](https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/07-Input_Validation_Testing/17-Testing_for_Host_Header_Injection)、[NIST SP 800-207](https://csrc.nist.gov/pubs/sp/800/207/final) |
| 書き手は 1 人、読み手は多数 | 共有の Postgres ではなく、書き込みは 1 台のハブ | [Leader and Followers](https://martinfowler.com/articles/patterns-of-distributed-systems/leader-follower.html)、『データ指向アプリケーションデザイン』5 章 |
| 結果まで書いた決定 | ハブだけが書き込む理由を記録する | [Documenting Architecture Decisions](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions) |

完全な一覧は『Software Architecture in Practice』（Bass、Clements、Kazman）の品質特性と戦術に沿わせ、1 つのアーカイブで
たまたま起きたことだけでなく、可用性、変更容易性、性能、セキュリティなどを網羅するようにします。チームは独自の原則と
参考文献を追加できます。

ほかにも、決まった一覧からタグを付けます。

- **セキュリティの教訓** には [MITRE CWE](https://cwe.mitre.org/) の ID を付けます。`Host` ヘッダーの事件は
  [CWE-807](https://cwe.mitre.org/data/definitions/807.html)（Reliance on Untrusted Inputs in a Security Decision）です。
- **エージェント自身についての教訓** には、[NIST AI 600-1 Generative AI Profile](https://doi.org/10.6028/NIST.AI.600-1)
  のリスク名を付けます。エージェントが記憶から数字を書いたなら、*confabulation*（作話）の事例です。
- **企業向けには、** この流れが [NIST SSDF](https://csrc.nist.gov/pubs/sp/800/218/final)（SP 800-218）に対応します。タスク
  RV.3.1 は根本原因を分析し、RV.3.2 は時間をかけてパターンを探し、RV.3.3 は「脆弱性のクラスを根絶する」ために似た問題が
  ないかソフトウェアを見直します。関連する事件の表示が RV.3.3 にあたります。

## 3. 思い出す形の週次レビュー

各コンピューターがすでに書いている週次レビューに、事件簿の形で 5 件を加えます。その週の新しいものが 2 件と、また出す時期に
なった古いものが 3 件です。どれも最後に「知っていた」か「知らなかった」、そして「すぐ」「あとで」「いつか」を選び、次に
出す時期が決まります。期限切れの件数は出さず、1 週休んでも未消化分は溜まりません。

## 4. チーム

- **メンバーが見える場所にチームメイトの教訓を。** プロジェクトのページと週次レビューに「チームメイトから」のバッジと
  絞り込みを付け、誰のセッションから来たかを示します。2 人が同じ教訓を述べたときは、2 つの事件を並べて見せます。
- **ハブで人ごとの件数を出さない。** チームのホームでは、人ごとの教訓の件数の代わりに、誰が何に取り組んだか（プロジェクトと
  話題、数字なし）を示します。教訓の件数は、その人のセッションでうまくいかなかったことの数にほぼ等しいからです。
- **今週の事件。** チームのホームに、gotcha だけでなく決定や成功も含めて 1 件を出し、みんなで読む定番にします。
- **メンバーが反応できる。** 役に立った、古い、知っていた。今はピンとめと非表示は管理者しかできません。「古い」には、
  コンピューター自身による「教訓のファイルが変わった」という確認も乗せます。ナレッジだけを受け取るハブは、ファイルのパスを
  知らないからです。
- **新しく来た人のための事件簿。** セッションがまだないプロジェクトでは「ここから始める」ページを出します。いちばん
  裏付けのある事件、決定とその理由、実行とデプロイの方法、誰に聞けばよいかです。

## 5. あなたのスキル

その人が取り組んだことと、わかっていると示したことを、セッションから組み立てる非公開のページです。

2 つの列を分けて見せます。あるスキルが出てきたセッションがあっても、その人がそのスキルを持っている証拠にはならないからです。

- **エージェントと取り組んだこと:** プロジェクト、ツール、出会った原則、生まれた教訓。
- **わかっていると示したこと:** 数週間後に正しく答えられた事件、エージェントより先に言い当てた原因、決めて記録した決定。

地図は決まったスキルの一覧に沿わせます。[SFIA 9](https://sfia-online.org/en/sfia-9) のスキル（Solution architecture、
Software design、Programming/software development など）、[NIST NICE Framework](https://www.nist.gov/itl/applied-cybersecurity/nice)
のタスク・知識・スキルの記述とワークロール（Secure Software Development など）、
[SWEBOK v4](https://www.computer.org/education/bodies-of-knowledge/software-engineering) の知識領域です。時間を追った成長
（扱った原則、減ってきた繰り返しの失敗）と、その人にとって新しい領域も、次のカタと参考文献付きで示します。

レベルは決して出しません。SFIA のレベルは責任、自律、影響力を表すもので、セッションからはわかりません。本人は、すべての
主張にセッションへのリンクを付けた「ブラッグドキュメント」の下書きとして書き出せます。自分の成長や評価面談のためのもので、
ハブには何も届きません。

## 効果の測り方

役に立ったかを尋ねると、ただ眺めるだけの一覧が良く見えてしまいます。そこで、思い出せたかと行動を測ります。

| 指標 | 中身 | 測る場所 |
|---|---|---|
| 飛ばした割合 | 1 人あたり 1 週間で飛ばした問いの割合 | 本人のコンピューター |
| 時間をおいた想起 | 初めて見てから 2〜6 週間後に事件に正しく答えられた割合 | 本人のコンピューター |
| 再発 | その人が見た教訓に結びつく「うまくいかないこと」の原因が、あとのセッションでまた起きるか | 本人のコンピューター（「うまくいかないこと」のカタログ） |
| 人が先に言い当てる | 同じ原因に当たったあとのセッションで、エージェントより先に本人が原因か修正を口にするか | 本人のコンピューター |
| 共有の健全さ | ハブを変える前と後で、ハブと共有されたセッションの割合 | ハブ（チーム全体の合計だけ） |

落とし穴が 1 つあります。gotcha が再発しなくなったのは、本人が学んだからではなく、セッション開始時のメモでエージェントが
防いだからかもしれません。そこで、エージェントには常にすべての教訓を渡し、本人に見せるものだけを変えます。対象の教訓ごとに、
先に問う、そのまま見せる、見せない、のどれかにします。一人ひとりの中で比べるので、5〜20 人のチームでも成り立ちます。1 と 3
より先を作る前に、Chronicle 自身の利用で 6〜8 週間試します。

## やらないこと

- ランキング、途切れると失われる連続記録、期限切れの件数、「gotcha が多い人」の表示。
- ハブでの人ごとの数字。管理者が人を評価するのに使えるものすべて。
- 週に 1 回を超える通知。
- モデルが作った原則、スキル、参考文献。
- セッションから推定したスキルのレベル。

## 語彙のライセンス

NIST の文書（SSDF、SP 800-207、AI 600-1、NICE）は米国政府の著作物で、引用できます。CWE は MITRE の利用規約のもとで無償で
使えます。OWASP の資料は CC BY-SA です。SFIA は個人と組織内での利用は無償ですが、製品に組み込む前に SFIA Foundation の
ライセンスを確認する必要があります。ISO/IEC 25010 は有償なので、品質特性の名前だけを使います。

## 作る順番

1. 現場と外れた手がかりを取り出す（理由付きの教訓）。
2. 事件簿と、教える前に問う問い。
3. 思い出す形の週次レビュー。上の指標を最初から組み込む。
4. ハブで、人ごとの件数の代わりに誰が何に取り組んだかを示す。チームメイトの教訓をメンバーのダッシュボードに出す。
5. アーキテクトの視点とトラック。
6. メンバーの反応、今週の事件、新しく来た人のための事件簿。
7. あなたのスキル。
